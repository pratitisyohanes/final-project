1. Analisa dokumen guideline

Guideline meminta satu website full-stack yang dikerjakan individu, dengan empat lingkup kerja: ERD & database, backend & API, frontend React, serta deployment & dokumentasi. Tema yang dipilih adalah Sistem Booking dan Manajemen Layanan: pengelolaan layanan, jadwal, pelanggan, dan riwayat transaksi booking.

Cuplikan schema Prisma

model Schedule {
  id          Int            @id @default(autoincrement())
  serviceId   Int            @map("service_id")
  date        DateTime       @db.Date
  startTime   String         @map("start_time") @db.VarChar(5)
  endTime     String         @map("end_time") @db.VarChar(5)
  capacity    Int            @default(1)
  bookedCount Int            @default(0) @map("booked_count")
  status      ScheduleStatus @default(AVAILABLE)
  service     Service        @relation(fields: [serviceId], references: [id])
  bookings    Booking[]

  @@unique([serviceId, date, startTime])
  @@index([date, status])
  @@map("schedules")
}

model Booking {
  id          String        @id @default(uuid())
  bookingCode String        @unique @map("booking_code")
  userId      String        @map("user_id")
  serviceId   Int           @map("service_id")
  scheduleId  Int           @map("schedule_id")
  totalPrice  Decimal       @map("total_price") @db.Decimal(12, 2)
  status      BookingStatus @default(PENDING)
  notes       String?
  createdAt   DateTime      @default(now()) @map("created_at")
  user        User          @relation(fields: [userId], references: [id])
  service     Service       @relation(fields: [serviceId], references: [id])
  schedule    Schedule      @relation(fields: [scheduleId], references: [id])
  payment     Payment?
  logs        BookingStatusLog[]

  @@index([userId, status])
  @@index([createdAt])
  @@map("bookings")
}

Index pada (date, status) dan created_at mempercepat filter waktu dan query laporan.

Error handling

Semua error dilempar sebagai ApiError(statusCode, message) dari service dan ditangkap satu errorHandler global. Controller dibungkus asyncHandler agar tidak perlu try/catch berulang.

KodeKapan dipakai
400Request tidak masuk akal secara bisnis (misal membatalkan booking yang sudah selesai).
401Token tidak ada, salah, atau kedaluwarsa.
403Role tidak cukup, atau user mengakses booking milik orang lain.
404Data tidak ditemukan.
409Konflik: email sudah terdaftar, slot penuh, jadwal bertabrakan.
422Input gagal validasi Zod.
429Terlalu banyak request (rate limit login).
500Error tak terduga. Detail hanya dicatat di log, tidak dikirim ke client.

Error Prisma juga diterjemahkan: P2002 (unique) menjadi 409 dan P2025 (record not found) menjadi 404.

Middleware auth & role

// middlewares/authenticate.js
const authenticate = (req, res, next) => {
  const header = req.headers.authorization || '';
  const token = header.startsWith('Bearer ') ? header.slice(7) : null;
  if (!token) throw new ApiError(401, 'Token tidak ditemukan');
  try {
    req.user = jwt.verify(token, env.JWT_ACCESS_SECRET); // { sub, role }
    next();
  } catch {
    throw new ApiError(401, 'Token tidak valid atau kedaluwarsa');
  }
};

// middlewares/authorize.js
const authorize = (...roles) => (req, res, next) => {
  if (!roles.includes(req.user.role)) throw new ApiError(403, 'Akses ditolak');
  next();
};

// contoh pemakaian di route
router.post('/', authenticate, authorize('ADMIN'), validate(createServiceSchema), controller.create);

7. Logika booking dan validasi jadwal

Bagian ini memenuhi poin guideline "validasi ketersediaan" dan "jadwal tidak bertabrakan", dan biasanya paling banyak ditanyakan mentor.

Aturan validasi

  1. Slot ada dan layanannya aktif. Jika tidak, 404.
  2. Slot belum lewat. Tanggal + jam mulai harus di masa depan, jika tidak 400.
  3. Slot berstatus AVAILABLE dan booked_count < capacity. Jika tidak, 409 "Slot sudah penuh".
  4. User belum punya booking aktif di slot yang sama. Mencegah double booking.
  5. Jadwal user tidak bertabrakan. User tidak boleh punya booking PENDING/CONFIRMED lain yang waktunya overlap pada tanggal yang sama.
  6. Semua langkah di dalam satu transaksi dengan baris slot dikunci, agar dua orang yang menekan "Booking" bersamaan tidak sama-sama lolos ke kuota terakhir.
Rumus tumpang tindih waktuDua rentang [Amulai, Aselesai) dan [Bmulai, Bselesai) bertabrakan bila A.mulai < B.selesai AND A.selesai > B.mulai. Rumus yang sama dipakai admin saat membuat slot baru untuk layanan yang sama.
// modules/bookings/booking.service.js — kerangka, lengkapi sendiri
async function createBooking(userId, { scheduleId, notes }) {
  return prisma.$transaction(async (tx) => {
    // 1. kunci baris slot agar tidak terjadi race condition
    const [slot] = await tx.$queryRaw`
      SELECT * FROM schedules WHERE id = ${scheduleId} FOR UPDATE`;
    if (!slot) throw new ApiError(404, 'Jadwal tidak ditemukan');

    // 2–3. cek waktu, status, kuota
    if (isPast(slot.date, slot.start_time)) throw new ApiError(400, 'Jadwal sudah lewat');
    if (slot.status !== 'AVAILABLE' || slot.booked_count >= slot.capacity)
      throw new ApiError(409, 'Slot sudah penuh');

    // 4–5. cek bentrok dengan booking aktif user
    const clash = await findOverlappingBooking(tx, userId, slot);
    if (clash) throw new ApiError(409, `Bentrok dengan booking ${clash.bookingCode}`);

    // 6. simpan booking, payment, log, dan update kuota
    const service = await tx.service.findUnique({ where: { id: slot.service_id } });
    const booking = await tx.booking.create({ data: { /* ... */ totalPrice: service.price } });
    const newCount = slot.booked_count + 1;
    await tx.schedule.update({
      where: { id: scheduleId },
      data: { bookedCount: newCount, status: newCount >= slot.capacity ? 'FULL' : 'AVAILABLE' },
    });
    return booking;
  });
}

Transisi yang diizinkan disimpan sebagai peta di kode, misalnya { PENDING: ['CONFIRMED','CANCELLED'], CONFIRMED: ['COMPLETED','CANCELLED'] }. Transisi lain ditolak dengan 400. Saat booking dibatalkan, booked_count dikurangi dan slot FULL kembali AVAILABLE, juga di dalam transaksi. Setiap transisi menulis baris ke booking_status_logs.

Alur auth di frontend

  1. Login berhasil: simpan user dan accessToken di Zustand. Refresh token disimpan di cookie httpOnly (lebih aman) atau localStorage (lebih sederhana).
  2. Axios request interceptor menambahkan header Authorization: Bearer ….
  3. Axios response interceptor: bila 401, panggil /auth/refresh sekali lalu ulangi request. Jika gagal, logout dan arahkan ke login.
  4. RoleRoute mengarahkan user non-admin yang membuka /admin ke halaman 403.
