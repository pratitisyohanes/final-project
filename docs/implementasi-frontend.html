Dokumen ini menjelaskan langkah demi langkah pembuatan folder frontend/ berdasarkan perancangan di rules/cek-requirement-dan-perancangan.html. Nama project, file, dan komentar kode memakai bahasa Inggris. Penjelasan memakai bahasa Indonesia.

Ringkasan hasil

  • Folder baru frontend/ berisi 72 file sumber: 13 halaman, 25 komponen, dan 8 file API.
  • Ada tiga area: publik (beranda, katalog, detail + pilih slot, login, register), pelanggan (booking saya, detail + batal, profil), dan admin panel (dashboard, booking, layanan, kategori, jadwal, pelanggan, laporan).
  • npm run build sukses. Halaman admin dipisah ke bundle sendiri, sehingga pelanggan tidak mengunduh library grafik.
  • Saya menguji integrasi dengan backend sungguhan dan database PostgreSQL sementara di port 55432, lalu mematikannya kembali. Database lokal Anda tidak disentuh.
  • Perubahan di luar frontend/ hanya satu: service web ditambahkan di backend/docker-compose.yml.

2

Lapisan API dan interceptor token

Semua komunikasi ke backend ada di folder src/api/. File client.js membuat instance Axios. Setiap modul backend punya satu file, misalnya services.api.js dan bookings.api.js.

// src/api/client.js (ringkas)
api.interceptors.request.use((config) => {
  const { accessToken } = useAuthStore.getState();
  if (accessToken) config.headers.Authorization = `Bearer ${accessToken}`;
  return config;
});

// 401 -> refresh sekali -> ulangi request; gagal -> hapus sesi
api.interceptors.response.use((res) => res, async (error) => { ... });
  • getData dan getList membuka envelope backend { success, message, data, meta }. Halaman cukup menerima data atau { items, meta }.
  • Beberapa request yang gagal 401 secara bersamaan berbagi satu panggilan /auth/refresh. Ini penting karena backend merotasi refresh token: token lama langsung dihapus setelah dipakai.
  • Download CSV memakai responseType: 'blob' karena endpoint butuh header token, sehingga tidak bisa memakai link biasa.

api/client.js · auth.api.js · categories.api.js · services.api.js · schedules.api.js · bookings.api.js · users.api.js · reports.api.js

3

Auth store dan pemulihan sesi

store/authStore.js (Zustand) menyimpan user, accessToken, dan refreshToken. Hanya user dan refreshToken yang disimpan ke localStorage. Access token cukup di memori karena umurnya hanya 15 menit.

Saat halaman di-reload, hooks/useSessionBootstrap.js menukar refresh token dengan access token baru sebelum aplikasi dirender. Tanpa langkah ini, halaman admin yang memakai optionalAuthenticate (misalnya daftar layanan) akan dimuat sebagai tamu dan hanya menampilkan layanan aktif.

store/authStore.js · hooks/useSessionBootstrap.js · hooks/useLogout.js · App.jsx · main.jsx

4

Hooks data: TanStack Query, mutasi, dan filter di URL

  • hooks/queries.js berisi semua query, seperti useServices, useMyBookings, dan useReportSummary. Query key dikumpulkan di objek queryKeys supaya mutasi tahu cache mana yang harus di-refresh.
  • hooks/useApiMutation.js membungkus useMutation: toast sukses, toast error, dan invalidateQueries. Error 422 tidak memunculkan toast karena pesannya ditampilkan di bawah field form.
  • hooks/useUrlFilters.js menyimpan search, filter, dan page di URL (?status=PENDING&page=2). Halaman bisa di-refresh atau dibagikan tanpa kehilangan filter. Mengubah filter otomatis kembali ke halaman 1.
  • hooks/useDebounce.js menunda pencarian 400 ms supaya tidak ada request di setiap ketikan.

6

Routing dan route guard

flowchart LR
  A[Request halaman] --> B{Sudah login?}
  B -- Belum --> C[/login + simpan halaman asal/]
  B -- Sudah --> D{Role sesuai?}
  D -- Tidak --> E[/forbidden 403/]
  D -- Ya --> F[Render halaman]
  C -- login sukses --> F
  • ProtectedRoute menerima prop roles, misalnya roles={['ADMIN']}. Komponen ini menggantikan RoleRoute yang ada di perancangan, supaya cukup satu komponen.
  • GuestRoute mencegah user yang sudah login membuka halaman login dan register.
  • Setelah login, user dikembalikan ke halaman asal. Contohnya, tamu yang menekan "Log in to book" kembali ke detail layanan.
  • Halaman admin dimuat dengan React.lazy.

10

File deployment

  • vercel.json: semua path diarahkan ke index.html, supaya refresh di /admin/bookings tidak menghasilkan 404.
  • Dockerfile dua tahap: build dengan Node, lalu disajikan dengan nginx. VITE_API_URL dikirim sebagai build arg karena Vite menanamkannya saat build.
  • nginx.conf: fallback SPA dan cache panjang untuk file di /assets.
  • backend/docker-compose.yml: ditambah service web di port 8080, dan CORS_ORIGIN api ditambah http://localhost:8080.
  • frontend/README.md: tech stack, cara menjalankan, struktur folder, daftar halaman, alur auth, dan deployment.

Cara menjalankan

# terminal 1 - backend (database lokal harus sudah di-migrate dan di-seed)
cd backend
npm run dev                  # http://localhost:5000

# terminal 2 - frontend
cd frontend
npm install                  # sudah dijalankan sekali
cp .env.example .env         # .env sudah dibuat, isinya VITE_API_URL=http://localhost:5000/api/v1
npm run dev                  # http://localhost:5173

Akun demo: admin@booking.com / Admin12345 dan budi@example.com / User12345.

Langkah berikutnya

  1. Jalankan migrate + seed di PostgreSQL lokal Anda, lalu coba semua alur di atas sendiri.
  2. Pelajari file inti sampai bisa dijelaskan: api/client.js, hooks/queries.js, hooks/useApiMutation.js, routes/ProtectedRoute.jsx, pages/public/ServiceDetailPage.jsx. Kebijakan guideline menyebut nilai 0 bila project terdeteksi 100% dibuat AI.
  3. Pindahkan .env.local keluar dari folder project, lalu git init dan push backend + frontend ke GitHub.
  4. Deploy: database (Neon/Supabase), backend (Render/Railway), frontend (Vercel). Set VITE_API_URL dan CORS_ORIGIN.
  5. README root, Postman collection, dan PPT.
